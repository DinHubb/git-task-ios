# Архитектура GitTask iOS

iOS-клиент для [GitTaskBot](https://github.com/Hadamot/GitTaskBot) — тот же функционал, что у Telegram-бота
(задачи в GitHub Issues, доска Projects v2, роли), но с нативным интерфейсом.

**Цель проекта — учебная:** освоить Swift, SwiftUI и архитектуру iOS-приложений на реальной задаче.
Поэтому каждый модуль описан в [`docs/modules/`](modules/).

**Сейчас:** только фронт на тестовых (mock) данных. Бэкенд (REST API в GitTaskBot) — позже.

---

## Выбранный подход: MVVM + Repository

```
┌──────────────┐   читает state,     ┌───────────────────┐   async-вызовы   ┌──────────────────────┐
│ View         │   вызывает методы   │ ViewModel         │ ───────────────▶ │ Repository (protocol)│
│ (SwiftUI)    │ ──────────────────▶ │ (@Observable)     │                  ├──────────────────────┤
│ только рисует│ ◀────────────────── │ состояние + логика│ ◀─────────────── │ MockTaskRepository   │ ← сейчас
└──────────────┘   SwiftUI сам       └───────────────────┘   данные/ошибки  │ APITaskRepository    │ ← потом
                   перерисовывает                                          └──────────────────────┘
```

| Слой | Отвечает за | Не должен |
|------|-------------|-----------|
| **View** | вёрстку, жесты, навигацию | содержать бизнес-логику, ходить за данными |
| **ViewModel** | состояние экрана, фильтры/сортировку, валидацию | знать про SwiftUI-вёрстку, про то, откуда данные |
| **Repository** | получение и сохранение данных | знать про экраны |
| **Model** | описание данных (`struct`, `enum`) | содержать логику загрузки |

**Почему так:** моки сейчас и настоящий API потом — это две реализации одного протокола.
Подмена делается в одном месте (`AppContainer`), ни View, ни ViewModel не меняются.

### Почему не TCA / VIPER
- **TCA** — отличная, но сторонняя библиотека со своим словарём; прячет, как работает сам SwiftUI. Изучать после базы.
- **VIPER / Clean** — 5+ файлов на экран; на нашем масштабе церемонии больше, чем пользы.

## Структура папок

```
gitTask/
├── App/                    # точка входа, сборка зависимостей (DI)
├── Core/
│   ├── Common/             # общие типы для экранов: LoadState
│   ├── Models/             # TaskItem, User, Priority, BoardColumn, Role
│   ├── Data/               # протоколы Repository + Mock-реализации
│   └── DesignSystem/       # цвета, бейджи, общие компоненты состояний
├── Features/               # по папке на фичу: View + ViewModel
│   ├── TaskList/
│   ├── TaskDetail/
│   ├── TaskFilters/
│   ├── NewTask/
│   ├── Profile/
│   └── Stats/
└── Resources/              # Assets (иконка, цвета)
```

**Правило зависимостей:** `Features → Core`. Core ничего не знает о Features; фичи не знают друг о друге.
Это «модульность папками»; позже эти границы станут Swift Packages.

Папки создаются в тот момент, когда в них появляется первый файл (пустые папки git не хранит).

## Ключевые решения

| Решение | Почему |
|---------|--------|
| SwiftUI, iOS 26+, только iPhone | современный стек, одна раскладка экрана для обучения |
| Swift 6, strict concurrency | компилятор ловит гонки данных на этапе сборки |
| `SWIFT_DEFAULT_ACTOR_ISOLATION = MainActor` | (дефолт Xcode 26) весь код по умолчанию на главном потоке — проще для UI; фоновую работу помечаем явно |
| `@Observable` вместо `ObservableObject` | новый механизм Observation: меньше кода, точечные перерисовки |
| `async throws` во всех методах репозиториев | когда придёт сеть, сигнатуры не изменятся |
| DI через инициализатор, без библиотек | понятно, тестируемо, без «магии» |
| `TaskItem`, а не `Task` | `Task` — встроенный тип Swift Concurrency |
| Модели и протоколы данных — `nonisolated` | их используют `actor`-репозитории вне главного потока |
| Язык разработки проекта — `ru` | системные форматтеры (даты «вчера», «послезавтра») говорят по-русски |
| Владелец ViewModel хранит её в `@State`, остальные получают через `let` | ViewModel не пересоздаётся при перерисовке |
| Соответствие `nonisolated`-протоколам в тестах — через `extension` | иначе изоляция протокола переносится на тип |
| `rawValue` enum'ов = строки бэкенда | JSON бота распарсится без ручного перевода |
| В `Core/Models` и `Core/Data` нет `import SwiftUI` | данные не знают, как выглядят на экране |
| Swift Testing для unit, XCTest для UI | новый фреймворк Apple; UI-тесты он пока не поддерживает |
| SwiftLint + SwiftFormat | стандарт коммерческих проектов: единый стиль, ловля типичных ошибок |

## Навигация (план)

```
TabView
├── 📋 Задачи      NavigationStack: TaskList → TaskDetail → Edit
│                  toolbar: фильтры (sheet), «+» (NewTask sheet)
├── 📊 Статистика  только admin/moderator
└── 👤 Профиль     роль, настройки списка
```

## Состояния экрана

Общий тип `LoadState<Value>`: `idle / loading / loaded(Value) / failed(Error)`.
Каждый экран показывает: загрузку (`ProgressView`), ошибку с «Повторить», пустой результат с подсказкой
(`ContentUnavailableView`), данные.

## Тестирование

- **Unit (Swift Testing):** ViewModel'и с mock-репозиториями — основной объём.
- **UI (XCTest):** smoke-тест запуска.
- **`#Preview`:** каждый экран во всех состояниях.

**Модуль готов, когда:** собирается без предупреждений SwiftLint, тесты зелёные, написан `docs/modules/NN-*.md`.
